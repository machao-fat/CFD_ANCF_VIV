# Real dynamic baseline and bounded non-zero prescribed-motion bridge V1

Date: 2026-09-09
Scope: one isolated, paired OpenFOAM test only. No ANCF participant, free
feedback, three-slice rerun, or long-time VIV calculation was started.

## Immutable context

`LOCAL_FIXED_ZERO_BRIDGE = FAIL_CLOSED` remains unchanged. The compatible-Uf
counterfactual is retained as an independent scientific result:

```text
ZERO_MOTION_INITIAL_FLUX_CAUSE = SUPPORTED_BY_COUNTERFACTUAL
```

It showed that the first fixed/dynamic zero-motion force difference is mainly

## Legal dynamic restart source

The source was the immutable native zero-motion continuation at
`runtime/fixed_cylinder_precursor_initialization_v1_run_002/zero_motion_dynamic_restart/0.105`.
It was generated by Foundation OpenFOAM 10 `pimpleFoam`, build
`10-c4cf895ad8fa`, with `displacementLaplacian` and zero boundary motion. It
naturally persisted `U`, `p`, `phi`, `Uf`, `meshPhi`, `pointDisplacement`,
`cellDisplacement`, `polyMesh/points`, and `uniform/time` at `0.105 s`.

Before use, the byte identities of `U/p/phi/Uf/meshPhi`, both displacement
fields, and the time-local mesh points were rechecked against the genuine
preCICE zero-motion case at the same time. They matched. The historical
native `fvSolution` lacks only the now-present `cellDisplacement` solver
sub-dictionary; the new pair consistently used the current preCICE zero-path
`fvSolution`, `fvSchemes`, properties, mesh, and `dt=0.005 s`.

This is therefore a real solver-produced dynamic restart state, not a
counterfactual or a copied static `Uf` initialisation. Its source identities
are in `runtime/cfd_current_dynamic_nonzero_bridge_v1_run_001/manifest.json`.

## Frozen paired bridge

Both cases started from the same `0.105 s` source state and ran to `0.605 s`
(100 steps). The prescribed physical motion was

```text
tau = t - 0.105 s
r(tau) = 0.5*(1-cos(pi*tau/0.1 s))  for 0 <= tau < 0.1 s; otherwise 1
y(t) = 0.1 m * r(tau) * sin(2*pi*0.16 Hz*tau)
```

The raised-cosine start makes both displacement and analytic velocity zero at
the restart instant. The frozen table gives the exact sampled motion sent to
both implementations; its discrete velocity is retained beside its analytic
velocity. The table is deliberately only 0.5 s long (less than one forcing
period), so it is an implementation bridge rather than a periodic-response
study.

| Path | Motion delivery |
|---|---|
| Native reference | `interpolatingSolidBody` plus the supported OF10 `sixDoFMotion` table |
| Current path | real preCICE adapter, `pointDisplacement`, and `displacementLaplacian` |

No requirement was imposed on interior mesh points or `meshPhi` being byte
identical: their interior mesh-deformation algorithms differ. The hard gates
were exact cylinder-boundary motion (`1e-9 m`), 100 steps, finite fields,
`Co <= 0.5`, `|global continuity| <= 1e-8`, no FPE/fatal/negative-volume
marker, and fields/meshPhi written at every output time. The 15% force L2
band was explicitly reporting-only, not an accuracy gate.

## Result: numerical execution completed, paired input identity failed

Both processes exited zero, wrote all 100 output times, and the prescribed
participant completed 100 preCICE windows. The native reference applied the
frozen motion exactly: maximum cylinder-centroid error was
`4.465e-13 m`. Both paths wrote `meshPhi`; neither log contained FPE, fatal,
NaN, or negative-volume evidence.

However, the current preCICE path did **not** consume the same physical input
layer as the native reference. At CFD output `0.110 s`, it still had the
initial zero displacement. At `0.115 s`, it had the sample labelled
`0.110 s`. This continued uniformly through the test:

```text
all 100 adapter CFD outputs consumed motion_plan[step-1]
native CFD output step consumed motion_plan[step]
```

For example, the participant wrote `y(0.110)=3.094244469e-06 m` before its
first `advance()`, while the adapter cylinder at `0.110 s` remained at
`0 m`; it received that sample at `0.115 s`. At the final output, native
reached `y(0.605)=0.048175367410 m`, while the adapter reached the prior
`y(0.600)=0.047734280882 m`. The maximum intended-time motion discrepancy
was `8.474e-04 m`, far beyond the `1e-9 m` hard gate.

Therefore:

```text
NONZERO_PRESCRIBED_BRIDGE_V1 = FAIL_CLOSED
MESH_METHOD_FORCE_COMPARISON = NOT_EVALUABLE
FIRST_BLOCKER = PRESCRIBED_PARTICIPANT_TIME_LAYER_MISMATCH
```

This is an observed test-participant/preCICE time-layer mismatch relative to
the native reference, not evidence that the adapter, the OF10 mesh-history
restore, force mapping, or either mesh mover is numerically defective. The
force comparison cannot be attributed to mesh-method differences while the
cylinder motions differ. Its retained descriptive values include relative L2
differences of `0.000739` for total Fx and `0.33723` for total Fy; the latter
is expected to be contaminated by the one-step transverse-motion lag.

## Quality evidence

Both runs stayed below the frozen Courant ceiling: maximum Co was
`0.35010195544`. Maximum absolute global continuity was `7.338e-11` for the
native path and `1.097e-10` for the adapter path.

At `0.605 s`, the adapter `checkMesh -allTopology -allGeometry` reported
`Mesh OK`, with minimum volume `1.560769e-03`, maximum non-orthogonality
`31.3575`, maximum skewness `0.503055`, and minimum determinant `0.530564`.
The native path had the same core geometry checks pass (minimum volume
`1.591108e-03`, maximum non-orthogonality `30.6437`, maximum skewness
`0.503020`, determinant `0.529907`). Its aggregate `checkMesh` status reports
one known two-dimensional-prism warning: 47 edges are not aligned with a
non-empty direction. This warning is retained, not hidden; it is the same
class documented for the expanded Gmsh prism mesh and is not a negative-volume
or core geometry failure.

## Decision

The real dynamic restart source is sufficient for a future bridge; no new
precursor is needed. The present bridge does **not** establish current
preCICE/displacementLaplacian versus native-interpolatingSolidBody force
agreement because their inputs were not time-aligned.

The minimal next action is a separately authorized, test-only participant
time-layer correction and one new paired bridge. It must predeclare the
initial and each subsequent preCICE payload so that the actual adapter CFD
output at `t_n` equals the same table value used by the native case at `t_n`.
The correction must first be shown in the participant event trace and the
written `pointDisplacement`/cylinder-centroid records; it must not change
OpenFOAM, the adapter, `dt`, PIMPLE, mesh, force mapping, ANCF, or the physics.
No such rerun was made here.

The current result is not a basis to enter independent single-slice free FSI.
